# 考试数据分析体系方案（grade-insight）

- 版本：v1（2026-10-23）｜ 承载规格：SPEC-002-月考分析数据融合方案-261023-082919.0504（spec-version 2，L2 方案稿，未动一码）
- 上游：v1 单月融合方案 `方案-月考分析数据融合.md`（其五层数据盘点、逐层可行性、风险表为本稿基座，本文不重复、只承接）
- 需求基线（用户 2026-10-23 五要点，原话见规格 1.1）：流水线固化 ｜ 手工录入兼容 ｜ 单考深度分析 ｜ 全量联合分析 ｜ 选科/志愿数据支持

## 一、需求解构 → 体系四层

用户的总体意图是形成一个**范式**：`收集 → 标准化 → 深挖 → 联合 → 决策支持`。解构为四层体系：

| 层 | 回答的问题 | 形态 |
|----|-----------|------|
| T1 数据资产层 | 一次考试的 raw 图片/手工数据，变成什么"可比较、可累积"的标准件 | 数据契约（目录约定 + exam.json schema）|
| T2 流水线层 | 每轮考试怎么"标准化提取、标准化输出"，且不随执行者漂移 | 固化件（提示词模板/校验脚本/准入清单/别名表，全部版本化）|
| T3 分析层 | 单考能看出什么、全部考试合起来能看出什么 | 单考深挖报告 + 联合分析（站内引擎 + 离线年报）|
| T4 决策层 | 对提升、选科、志愿分别给出什么强度支持 | 优先级补救清单 → 选科适配 → 志愿外源规划 |

核心设计判断：**分析体系的成败在 T1 数据契约，不在算法**。grade-insight 现有 analysis.js（三重归一+趋势/偏科/目标推演）已能覆盖大半 T3，缺的是它吃不到的数据层（题级/知识点）和一个让数据"月月可比"的契约。

## 二、T1 数据契约（方案核心，供实施规格直接引用）

### 2.1 目录约定（每轮考试一目录，同构复制）

```
grade-insight/details/<学段>/<学期>/<YYYY-MM>-<第N考>/
  raw/                 # 原始截图（命名容忍，准入清单校验）
  md/  (+md/images/)   # 转写件（SPEC-000 纪律产物，人读）
  data/exam.json       # ★ 标准化考试档案（机器读，分析事实源）
  data/report.md       # 单考深挖报告（T3 产物，人读）
```

10 月目录按此契约**回填**（首期即验证契约，见路线图阶段 1）。

### 2.2 exam.json 契约（gi-exam-data/1）

```
contract: "gi-exam-data/1"
meta:    { source: "raw"|"manual", pipeline: {transcribeTpl: "vN", converter: "vN"},
           transcribedAt, confidence: {按科的转写置信档: 高|中|低} }
exam:    { id, name, date, term, type, note }         # 同 store.js v1 字段
total:   { score, full, level, rank, rankSize }
subjects[]:
  { key, full, score, level,                          # L1 成绩层（必填）
    avgClass, avgGrade, rank, rankSize,               #    （有则填，无则缺省）
    questions[]: { no, type, point, diff, score,      # L2 题级层（9/9 科可提取）
                   mine, ref, correct,                #    （correct=mine≡ref 判定）
                   kpIds[], analysisRef, imgRefs[] }, # L4 索引：题目→知识点→解析文档/裁剪图
    kps[]: { kpId, name, rate, wrong, key } }         # L3 知识点层（源仅数学/生物，见 2.3）
integrity: { perSubject: 题分之和==L1得分, kpBadgeVsRows, totalSum, notes[] }  # 对账结果存档
```

- **兼容矩阵（手工录入）**：`source:"manual"` 时必填仅 L1（subjects[].score/full），其余层缺省；分析能力按层降级——只有 L1 时：趋势/偏科/百分位/目标推演可用（现系统全部功能）；有 L2：加题型×难度丢分矩阵；有 L3：加知识点画像与跨考核踪；有 L4：错题可点开题解。缺层不报错、不冒充（对齐 SPEC-000"不编造"纪律）。
- **kpId 与别名表**：知识点名称经 `grade-insight/data/knowledge-alias.yaml`（受控别名表）归一为稳定 kpId；归一失败的行保留原名并标 `unmapped:true`，**禁止模糊自动合并**（v1 已实证别名漂移：数学两处平面角命名不同）。
- 站点快照（localStorage/Netlify）只承接 **L1+L3 摘要**；L2/L4 全量留在 `exam.json` 静态文件（体积与同步写放大依据 v1 §二/§三，系统尺度下"全量入快照"正式排除）。

## 三、T2 固化流水线（五步，每步产物与门禁明确）

| 步 | 动作 | 执行体 | 固化件与版本 |
|----|------|--------|------------|
| S1 准入 | 对照**准入清单**核 raw：9 科成绩概览必含；知识点/试卷解析按科可选；命名容忍表兜底 | 脚本 | `pipeline/acceptance.yaml` vN |
| S2 转写 | raw→md（含配图裁剪嵌入）——即 SPEC-000 已验证的批量分组+忠实转写纪律 | AI 多模态（**不用本地 OCR**，同 SPEC-000 决策） | `pipeline/transcribe-prompt.md` v1（由 SPEC-000 实践提炼：忠实/表格/LaTeX/存疑标注/长图分带）|
| S3 转换 | md 表格→exam.json 草案 + 别名归一 + integrity 对账（题分之和 vs 成绩层、总分自洽） | 脚本（确定性） | `pipeline/convert.js`+`knowledge-alias.yaml` vN |
| S4 人审 | 处理转写存疑清单与对账失败项（S3 输出 fail list，人裁定后回填） | 家长/学生 | 存疑清单格式固定 |
| S5 交付 | ①exam.json+report.md 入库 ②站点导入包（快照 L1+L3）③联合分析数据集自动纳入 | 脚本 | 导入包=SPEC-001 先例格式 |

- **漂移防护**：exam.json 的 meta 记录本轮所用固化件版本；任何固化件升版（vN→vN+1）须对历史考**重跑 S3 对账回归**，防止"月月口径悄悄变了"。
- 手工录入走 S3'（UI 表单/导入包直接产出同契约 exam.json 等价物），与 raw 管线汇入同一 T3——这就是"兼容"的落点：兼容的是**契约**，不是来源。

## 四、T3 分析框架

### 4.1 单考深挖（`data/report.md`，每考自动生成+人审注记）

1. **丢分结构**：科目×题型×难度矩阵（源自 L2），绝对丢分与相对（对满分/难度）双口径；
2. **知识点画像**：薄弱 top-N（含【重点】置顶标记）、待提升、疑似错因（题目→kpIds 反查，仅 2/9 科有源时如实标注覆盖面）；
3. **对账与置信**：integrity 结果、转写存疑汇总（分析结论的"可信度脚注"）；
4. **中文小结**：亮点/漏洞/异常三段，模板化句式（确定性输出，不依赖模型即兴，保证跨考可比）。

### 4.2 联合分析（站点 analysis.js 扩展 + 年度/阶段离线年报）

1. **趋势**：现有三重归一（得分率/百分位/vsAvg）不动；新增**知识点掌握率跨考核踪**（kpId 对齐后同型问题）与**薄弱点老化**指标（同一 kpId 连续 N 考 rate<60% 即告警）；
2. **风险预警**：偏科发散斜率（科间得分率差走势）、波动率突增、排名百分位滑坡、均分口径突变（rankSize 变化时自动提示"分母变了，跨考比较降级"）；
3. **指引**：目标差距推演（已有 targetRate）× 薄弱点提分杠杆排序（分值权重×改善成本粗估）→ **优先级补救清单**（每次大考后输出 top5）；
4. **盘点**：跨考对照总表（科×考矩阵、题型丢分演变）——"可分析、盘点、发现问题、预知风险"的直接承接。

## 五、T4 决策支持路线（选科/志愿——诚实的强度分级）

| 支持 | 数据条件 | 可行性 |
|------|---------|--------|
| 选科适配（物化生/史地政组合） | 高一 4–6 次考的各科归一分**趋势斜率**+知识广度+稳定性；同 cohort 百分位 | **中期内真实可行**（高一数据量足够起步）；输出建议+置信说明，不代决 |
| 志愿·分数段-位次换算 | 校内排名→市排名需要换算基数（选科后分流人数） | 本地可建模，但需学校在考后提供分母口径（手工字段，准入清单加一项） |
| 志愿·院校/录取数据 | 高考录取线/一分一段表等**外部数据源** | 本体系外；与 query-system（已有中考志愿数据端）同型问题，属独立新规格；grade-insight 侧只保证产出标准件：历次归一分曲线+位次估计 |

原则：决策层只承诺"数据支持"，不承诺"预测"——置信脚注（转写质量、分母口径、样本数）随每条结论输出。

## 六、演进路线图（每阶段 = 一个实施规格的量级）

- **阶段 0 契约与固化件**：数据契约文档定稿、`transcribe-prompt.md` v1、`acceptance.yaml`、`knowledge-alias.yaml` 种子（数学 45+生物 21 条起步）、对账规则清单。产出全是文档+配置（L1 级实现）。
- **阶段 1 10 月回填打通**：`convert.js` + 单测，对 10 月 md 跑出首份 `exam.json`+`report.md`，人工全量抽检一次（契约验收）。此后每月月考走增量流水线（约 1 次/月，人工≈半小时审存疑）。
- **阶段 2 站点融合**：schema v2（normalize 扩字段、向后兼容）、知识点/题型视图、错题本联动（v1 方案 P1/P2 在此落地）、手工录入同契约。
- **阶段 3 联合分析**：跨考核踪/老化告警/补救清单上站；年报离线件。
- **阶段 4 决策支持**（远期，另立）：选科模块；志愿外源数据接洽（与 query-system 复用模式）。

## 七、风险表（v1 R1–R5 之外，体系新增）

| # | 风险 | 缓解 |
|---|------|------|
| R6 | **假精确**：别名归一/转写误差进入跨考趋势，看似科学实则失真 | unmapped 透明化；integrity 存档随数据走；报告带置信脚注；固化件升版跑历史回归 |
| R7 | 数据断层：知识点/题解仅 2/9 科有源，联合分析覆盖面被误读 | 分析输出显式标"数据源覆盖"，缺层降级不冒充（§2.2） |
| R8 | 流水线漂移：换会话/换执行者做转写，风格与口径逐月不一 | 固化件版本化+meta 记录+回归（T2 设计即为此）|
| R9 | 录入疲劳：每月审存疑清单若过重，范式会中断 | S4 只审"对账失败+高影响项"；原卷类 L5 不入分析，审读面可控 |

## 八、待决策点（人工裁定后按阶段另立实施规格；裁定前本方案不动一码）

1. **E1 存储拓扑**：快照仅 L1+L3、L2/L4 走 exam.json 静态懒加载（**建议**）vs 全量入快照（系统尺度下不建议，v1 D2 由此更新）；
2. **E2 转换器形态**：仓库 Node 脚本+单测（**建议**，确定性）vs 每轮由 AI 现场转换（不可比）；
3. **E3 单考深挖载体**：`data/report.md` 仓库文档（**建议**起步）vs 直接做站点页 vs 双轨；
4. **E4 别名表起点**：种子=本月两科实名+增量维护（**建议**）vs 预建高中全科知识点词表（重，缓议）；
5. **E5 手工录入最小集**：仅 L1（**建议**）vs 要求手填题级（不现实）；
6. **E6 推进节奏**：先批阶段 0+1（纯 repo 文档/脚本/数据件，不碰站点），验证契约后再批阶段 2+（**建议**）vs 一次批到阶段 3。
