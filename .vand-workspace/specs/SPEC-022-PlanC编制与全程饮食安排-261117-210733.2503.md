# 一、Requirements（产品视角 · 意图作者填写）

## 1.1 背景与问题

用户会话拍板："基本选定planA+H10酒店，又想同时去平海古城，请编制PlanC：planA+H10+平海古城，并补充全程具体的早午晚饮食安排。" 现状：页面行程方案仅 A/B 两案，且两案均无逐餐安排；H10 盐晶（情人湾内、住客免票、套餐含 2 大 2 小早晚）与平海古城（距盐晶约 6.5km·15min，SPEC-018 核实坐标）的组合地理可行：Day2 黑排角→古城→情人湾闭环约 28km 本地车程。

相似规格互链（背景证据，不承其范围）：SPEC-018（坐标/车程底数）、SPEC-021 v2/v3（黑排角分段与情人岛攻略）、SPEC-020（一页纸③出片体验派——C 为其古城扩展版，联动一行交叉引用）。

## 1.2 目标用户与场景

全家按 C 案出行：内容=A 案全部玩法 + 平海古城 + 住情人湾；需要一张从 D1 早餐到 D2 晚餐的逐餐安排（含店家候选与预算）。

## 1.3 业务价值与成功指标

现状 = 首次观测（2026-11-17）：无 C 案、无逐餐表。指标：①方案选择器出现第三案并可切换（沿用既有 JS）；②C 案含 Day2 时间表（含潮汐弹性提示）+ 时间轴 + 费用估算；③全程 7 餐（D1 早/午/晚、D2 早/午/下午茶/晚）逐餐落实（在哪吃/吃什么/候选店/预算），店家均标注来源与"出发前核实"；④一页纸③卡加一行 C 案交叉引用；⑤A/B 两案零改动。

## 1.4 用户故事

- P0 作为决策者，我希望一屏看到 C 案完整两天动线（含住宿地点变化带来的顺序调整），以便确认比 A 多古城后节奏是否可接受。
- P0 作为全家，我希望每顿饭都有着落（店名候选+预算），以便出发不再临场找店。
- P1 作为执行者，我希望知道潮汐不利时的降级顺序，以便当日临场调整。

## 1.5 验收标准（可验证）

- AC1（行为型）：Given 行程方案节 When 点选「方案 C」Then 显示 C 案内容（时间表 + 时间轴 + 费用卡），A/B 内容与切换不受影响。【验证方式：grep + 目检】
- AC2（行为型）：Given C 案 When 渲染 Then 含 7 餐饮食安排卡（D1 早/午/晚、D2 早/午/下午茶/到家晚），每餐含地点/内容/候选店（港口：金汇海景/指景/一线海景；平海：金源湾海鲜酒楼/老市场小吃）与预算小计。【验证方式：grep + 目检】
- AC3（边界型）：Given 潮汐不利情形 When 查看 C 案 Then 有明确弹性预案（低潮点偏下午时的对调/让位顺序）。【验证方式：grep】
- AC4（边界型）：Given A/B 案与一页纸 When 对比改动 Then A/B 零改动；一页纸仅③卡增加一行交叉引用。【验证方式：git diff 断言】

## 1.6 体验意图

C 案标识色沿用 A 线橙色系但加深区分（#c2410c）；节奏标签"内容最满·两案玩法合一"；饮食卡用既有 tips-box 语言，逐餐一行一信息，店家带"2026-11 在册/出发前核实"口径。

## 1.7 非目标（本期明确不做）

- 不重制 A/B 案内容与决策地图（C 的地理=A 图+B 图④，图上已有全部点位）；
- 不新增地图文件；
- 不改酒店推荐节细节（一页纸仅加一行交叉引用）；
- 不预订/不核实店家营业状态（标注口径即可）。
