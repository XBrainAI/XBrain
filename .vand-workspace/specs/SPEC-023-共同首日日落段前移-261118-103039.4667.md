# 一、Requirements（产品视角 · 意图作者填写）

## 1.1 背景与问题

用户提议（2026-11-18 原话）：共同首日的【大星山观景台/情人堤日落】与【海鲜晚餐+海滩散步消食】**对调——饭后再去大星山和情人堤**，并要求"评估是否合适，如合适请调整，如不合适请提供调整方案"。评估结论：原样对调**不合适**——① 日落锚点不可移动（11–12 月惠东日落 ≈17:35–17:50，页内原按 8 月 19:05 排）；② 大星山盘山路无照明，夜间带娃上山不安全且"俯瞰双湾"景观归零。变通：日落两点位前移、晚餐提前至 18:15、饭后段改为情人堤夜堤听涛/海滩散步消食（用户"饭后出门"诉求由夜散步承担）。

相似规格互链（背景证据，不承其范围）：SPEC-022（Plan C 首日微调卡时间联动）、SPEC-021（情人岛/黑排角，不涉及）。

## 1.2 目标用户与场景

三案共同首日（A/B/C 共用 #day1 块 + C 首日卡）：傍晚段按"锚定日落"重排，冬夏两季口径都标注。

## 1.3 业务价值与成功指标

现状 = 首次观测（2026-11-18）：首日傍晚段为 8 月口径（15:30 出门 / 17:30 情人堤 / 19:00 晚餐）。指标：#day1 表+时间轴与 C 首日卡改为「16:50 观景台（日落前 45min）→ 17:35 情人堤日落 → 18:15 晚餐 → 饭后夜堤/海滩消食」，附冬季(≈17:40)/夏季(≈19:05)双口径与"为何不饭后上山"一行说明；其余段零改动。

## 1.4 用户故事

- P0 作为全家，我希望晚饭后还能轻松出门走走（夜堤听涛/海滩），以便消化与收尾不赶。
- P0 作为全家，我希望日落与观景台都看到，以便不因对调损失核心景观。

## 1.5 验收标准（可验证）

- AC1（行为型）：Given #day1 时间表与时间轴 When 渲染 Then 傍晚段为 观景台(16:50)→情人堤日落(17:35)→晚餐(18:15)→饭后夜散步，且含冬/夏日落双口径注。【验证方式：grep + 目检】
- AC2（边界型）：Given 用户原提议（饭后上山）When 查看说明 Then 页面有一行"为何不饭后上山"的安全口径（盘山路无照明/天黑无景观）。【验证方式：grep】
- AC3（边界型）：Given C 案首日卡 When 渲染 Then 时间与新首日段一致（16:50/17:35/18:15）。【验证方式：grep】

## 1.6 体验意图

时间轴文案解释"锚定日落"逻辑一句话，不展开说教；夜散步段给"情人堤夜堤听涛/蓝眼泪季(4-6月)提示"彩蛋。

## 1.7 非目标（本期明确不做）

- 不改 A/B/C 案 Day2 与其他节；
- 不全页季节重写（仅傍晚段双口径括注）；
- 不改天气节风险表（"D1 傍晚 落日 情人堤"仍成立）。
