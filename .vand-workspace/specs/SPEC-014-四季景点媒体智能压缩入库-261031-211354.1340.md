# 一、Requirements（产品视角 · 意图作者填写）

## 1.1 背景与问题

用户原话："由于视频、图片可能较大，一方面 github 上传不了，另一方面页面加载比较慢，所以整个四季景点范围下上传的照片视频都需要进行智能判断采取必要的压缩。"

**现状核验（2026-10-31 实测，证据可复核）**：

| 事实 | 实测值 | 证据 |
|------|--------|------|
| 四季景点媒体总量 | 525 个 / 1,584.2 MB | `Get-ChildItem 四季景点 -Recurse` 按媒体扩展名统计 |
| 视频 | 47 个 / 679.5 MB，最大单文件 **70.9 MB** | `四季景点/深圳周末家庭游/游记/美高梅酒店-沙滩兄弟-VID_20260711_172701.mp4`，已逼近 GitHub 单文件 100MB 硬限 |
| 图片 | 478 个 / 904.8 MB，其中 **>3MB 的 87 个 / 405.9 MB** | 分辨率普遍 3072×4096 / 4032×3024（1200 万像素手机原图），单张 6.3–13.3 MB |
| 现有压缩服务盲点 | 只重编码、**不缩放分辨率**（`src/compress_media.sh` 无 `-vf scale`）；不支持 HEIC 输入；无"已达标跳过"幂等逻辑 | `src/compress_media.sh` 第 129–172 行 `compress_image` / `compress_video` |

| 生成器 | `gen_travelogue.py` / `gen_life_record.py` 均无压缩调用 | 源码检索 `compress|ffmpeg|heif` 零命中 |
| 流程文档 | 四季景点「新增景点流程」未包含压缩步骤，仅靠通用媒体入库纪律 | `.vand-workspace/project-context.md` 第 1601–1614 行 |

后果：① 新增 4K 视频与 12MP 原图会持续推高仓库体积（二进制入库后旧版本永久占用历史）；② 移动端单张 6–13MB 图片首屏即卡顿；③ 靠人工判断"哪些需要压、压到什么程度"不可持续，容易漏压或过度压缩。

相似规格互链（背景证据，不承其范围）：扫描 `specs/` 全部 21 份规格，**无媒体压缩/图片处理类规格**（既有规格集中于月考与考情分析、全站 UI 重构、行程与子站页面），故本任务为新规格。

**用户决策（2026-10-31 会话确认，原话留痕）**：
1. 治理范围："只约束新增素材"——存量 1.58GB 一律不动。
2. 图片策略："请结合 github 上传的限制特性以及移动端加载性能综合推荐"→ 授权按作者综合推荐执行（长边 ≤2048 + Q85）。
3. 视频策略："1080p上限 + CRF23（推荐）"。
4. 执行形态："增强一键服务+流程规范（推荐）"——扩展统一入口并按类型/体积/分辨率智能判定，写入生成页面前的必跑步骤。

**AUDIT-012 承接与二次裁定（2026-10-31，会话原话留痕）**：回执结论 = **有条件通过**（K3/K5/K6/K7/K10 不通过；阻塞项 B1 PNG 800KB 不可达、B2 HEIC 移出与既有规则/存量冲突、B3 "仅新增"无执行机制、B4 幂等承诺覆盖不足）。用户对未决问题裁定：① 无透明通道的照片型 PNG **转 JPEG**（截屏/图表型保留 PNG）；② HEIC 用**显式开关 + 备份移出**；③ "仅新增"以 **git 未跟踪文件**为准；④ 幂等由**状态清单**保证。据此修订为 v2 并重走意图评审（AUDIT-013）。

- AC1（行为型·自动化测试）Given 一批混合素材（>3MB 的 4096px 大图、<200KB 小图、含透明 PNG、不透明照片型 PNG、不透明截屏/图表型 PNG、4K 视频、HEVC 视频、已达标图片/视频）When 执行统一压缩入口 Then 逐个自动选择策略：JPEG 缩至长边 ≤2048 + Q85 + 去 EXIF；小图与已达标文件跳过；含透明 PNG 保留 PNG 只缩长边；无 alpha 且颜色数 ≥4096 的照片型 PNG 转 JPEG Q85 并改名为 `.jpg`；无 alpha 且颜色数 <4096 的截屏/图表型 PNG 保留 PNG 只缩长边；4K 视频缩至短边 ≤1080 + CRF23 + faststart；HEVC 强制转 H.264；音轨保留。
- AC2（边界型·自动化测试）Given `--dry-run` When 执行 Then 不写任何文件；Given 压缩收益低于门槛或 ffmpeg 编码失败 When 处理 Then 保留原文件并输出跳过/失败原因；Given 同一目录以相同参数连续执行两次 When 第二次执行 Then 实际改动文件数为 0（状态清单命中即跳过，幂等）；Given 处理后仍超目标上限 Then 状态清单标记 `over-limit` 并告警，后续运行不再反复重编码（除非 `--force`）。
- AC3（边界型·自动化测试）Given `--backup-dir DIR` When 实际替换原件 Then 原件按相对路径镜像备份到 DIR，备份件字节与原文件一致；Given 目录内含 `.heic` 且**未传 `--heic`** Then 不转换、明确提示需显式开启，原档原地不动；Given 传 `--heic` When 处理 Then 转换出的 `.jpg` 参与压缩，原 `.heic` 移入 `--backup-dir`（未指定时移入按项目根解析的默认备份目录 `<repo>/../_media_bak/`）且工作树内不再存在；Given 运行环境缺少 `pillow-heif` Then 明确提示跳过原因而非静默失败。

- AC5（行为型·事实核证）Given 文档 When 维护者新增子站/游记/规划 Then 以下三处同步更新且口径一致：`src/README.md` §10（含 §10.4 的 HEIC 边界改写）、`.vand-workspace/project-context.md` 第 18 行摘要与第 443 行 HEIC 处理段、同文件四季景点新增景点流程段；明确「HEIC 转 JPEG（`--heic`）→ 统一入口压缩（先 dry-run 后实压，`--only-new`）→ 生成/编制页面 → 校验 → 提交」顺序，并载明生成器不自动压缩。

# 二、Design（技术视角 · Conductor 填写）

## 2.1 方案概述

在既有 `src/compress_media.sh`（核心算法）+ `src/compress_media.py`（Windows 服务入口）上做**向后兼容增强**，不新建平行工具：

1. **图片策略**：新增 `--max-long-edge N`（默认 0 = 不缩放，保持旧行为）。四季景点 profile 取值 2048：`-vf scale='min(2048,iw)':'min(2048,ih)':force_original_aspect_ratio=decrease`（仅缩小，不放大），JPEG 沿用 `-q:v 3`（≈Q85）+ 默认去 EXIF。**PNG 判定（B1 闭合）**：含 alpha → 保留 PNG，只缩长边 + `-compression_level 9`；无 alpha 且颜色数 ≥4096（缩略至 256×256 后 `getcolors` 统计）→ 视为照片型，转 JPEG Q85 且文件名扩展名改为 `.jpg`（新增素材尚未编制页面，改名不破坏引用）；无 alpha 且颜色数 <4096 → 视为截屏/图表型，保留 PNG 只缩长边。
2. **视频策略**：新增 `--max-short-edge N`（默认 0 = 不缩放）与 `--crf-video N`（默认沿用现有 20）。四季景点 profile 取短边 1080 + CRF23 + preset medium（现有 slow 对 47 段视频过慢）；短边判定取 `ffprobe` 的 `min(width,height)`，竖屏不会因限"高"被压成 607×1080。H.264 输出、yuv420p、faststart、音轨 copy/aac 128k 逻辑沿用现状；HEVC 强制转码不变。**80MB 是软目标**：编码后 `ffprobe` 复检，超限则告警并在状态清单标记 `over-limit`（不静默失败、不无限重编码）；CRF23+medium 相对既有 CRF20+slow 的降画质换体积/速度取舍在 §10 显式声明。
3. **幂等与状态清单（B4 闭合）**：状态文件默认 `<backup-dir>/.compress-state.json`（未指定备份目录时 `<repo>/../_media_bak/.compress-state.json`，在仓库外、不入库）。记录每条文件的相对路径、size、mtime、参数指纹（profile + 关键参数哈希）与结果（`done` / `skipped` / `over-limit` / `failed`）。同参数重复运行命中即跳过；`--force` 忽略状态重做。达标判定本身仍保留为“未命中状态时的快速预检”：图片长边 ≤ `--max-long-edge` 且体积 ≤ `--target-max-kb`（默认 800）；视频编码 ∈ {h264} 且短边 ≤ `--max-short-edge` 且体积 ≤ `--target-max-mb`（默认 80）。
4. **HEIC 显式开关（B2 闭合）**：新增 `--heic`（默认关闭）。未开启时 `.heic/.heif` 仅提示“需显式开启 `--heic`”、原档不动（既有调用与存量跟踪的 HEIC 零影响）；开启时在 Python 入口先转 JPEG（`pillow-heif`，最长边与 `--max-long-edge` 一致、Q85），再交由 `.sh` 压缩，原 `.heic` 移入备份目录（按项目根解析，不随 CWD 漂移），工作树内不保留；`pillow-heif` 缺失时提示跳过。**解释器约束**：`pillow-heif` 仅存在于系统 Python 3.10（`C:/Users/km/AppData/Local/Programs/Python/Python310/python.exe`），HEIC 转换须用该解释器；非 HEIC 素材用任一 Python 运行均可。
5. **仅新增机制（B3 闭合）**：新增 `--only-new`，只处理 `git ls-files --others --exclude-standard` 列出的未跟踪媒体（即“尚未 `git add`”的文件）；流程固定“先压缩再 `git add`”。非 git 目录或命令失败时打印告警并回退为全目录处理（需显式确认）。
6. **参数优先级与存量缺陷收敛（N1 闭合）**：优先级 = 内置默认 < `--profile` < 显式参数；`--crf-video` 与既有 `--crf-h264` 同时出现时以前者为准并打印生效值；`FORCE_COMMIT` 由全局变量收敛为 `commit()` 入参，消除“HEVC 视频之后的图片继承强制替换”的存量缺陷；`--target-max-*` 仅作为达标预检与告警，不改变既有 `--min-saving` / `--min-size` 安全阀语义。
7. **profile 封装**：新增 `--profile scenic`，一次性套用**数值型参数**（长边 2048、短边 1080、CRF23、preset medium、目标 800KB/80MB）；`--only-new` 与 `--heic` 属**行为开关**，profile 不自动开启、需显式传入。不传 profile 时全部默认值 = 现有行为（零回归）。
8. **流程固化**：更新 `src/README.md` §10、`.vand-workspace/project-context.md` 第 18 行摘要、第 443 行 HEIC 段与四季景点新增景点流程段，把“先压缩后编制页面”写成必跑步骤并给出四季景点示例命令（`--only-new --heic --profile scenic`）。

**图片参数推荐依据**（用户授权综合推荐 + 实测）：长边 2048 在 3x DPR 手机（390 CSS px → 1170 物理 px）全屏与灯箱下约 1.75 倍余量；12MP 原图缩放后像素降至 1/4，配合 Q85 与去 EXIF 实测通常落 300–600KB。实测四季景点 PNG 194 个 / 373.1MB，其中无 alpha 192 个 / 371.7MB、>800KB 者 169 个 / 363.7MB，大图颜色数采样 35k–59k（照片型），故“无 alpha 照片型 PNG 转 JPEG”是体积收益最大的处置；截屏/图表型颜色数低，保留 PNG 以免文字伪影。

- 文档回滚：同步 revert 文档提交。
- 无不可逆变更（不删除任何原件：替换件进 `--backup-dir`，HEIC 原档移入备份目录而非删除）。
