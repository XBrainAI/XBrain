# 一、Requirements（产品视角 · 意图作者填写）

## 1.1 背景与问题

用户需求原话："计划制定四季景点新行程计划，分析候选线路：清远上岳古村、观音山王寺，以及与之临近的景点"（"王寺"按上下文判读为"王山寺"，佛冈观音山景区内寺院）。`四季景点/待出行方案/清远佛冈自驾一日游计划.md`（8月盛夏版：上午观音山避暑、下午上岳避晒）**尚未执行**；时值 10 月底入秋冬，季节要素已变（温泉开季、荷花已谢、红枫将启），需按新季节与"一日往返"形态重做候选线路分析。

相似规格互链（背景证据，不承其范围）：SPEC-2026-0005《国庆收官日（2026-10-07）家庭一日游候选挖掘与行程推荐》——同交付范式（先候选对比、km 圈定后续出完整行程）、同落位 `四季景点/待出行方案/`，但出行日期与候选域不同，非同一任务，故另立本规格。

## 1.2 用户确认记录（2026-10-30 会话，AskUserQuestion 实答）

- **去过清单（§11.9 铁律）**：森波拉去过、温泉类（熹乐谷/聚龙湾）去过；**上岳古村、观音山王山寺、田野绿世界均未去过**（8月版计划未执行）。
- **出行形态**：只要一日往返。
- **时间窗口**：11月首个周末（2026-10-31 周六 / 11-01 周日）。

## 1.3 目标用户与场景

家庭四人（爸驾车、妈、哥、弟，常住荔湾西村），一日往返，早出晚归。

## 1.4 业务价值与成功指标

现状 = 首次观测（2026-10-30）：8月版计划在库未执行。指标：候选线路 ≥2 条（各含时间闭合的行程骨架），锚点与临近景点开放/门票/营业状态带来源与访问日期，10-31/11-01 天气联网核实，供 km 圈定后续出完整行程。

## 1.5 验收标准（可验证）

- AC1（事实核证型）Given 方案定稿 When 逐条核对关键事实 Then 开放/门票/营业状态/车程/天气均带来源与访问日期（2026-10-30）；无法核实的显式标注"待现场确认"并给出降级办法。验证方式：对照来源清单核查。
- AC2（行为型）Given 候选线路 When 阅读对比表 Then ≥2 条线路（含"为何选/为何不选"），已去过的（森波拉/温泉类）不作主推、仅作顺路彩蛋。验证方式：逐档核对。
- AC3（行为型）Given 各线路行程骨架 When 逐段推演 Then 时间闭合（约 07:00–07:30 出发、当日返抵西村），每段含车程估算并标注"以当日导航为准"。验证方式：逐段推演。
- AC4（边界型）Given 交付物 When 检查落位 Then 位于 `四季景点/待出行方案/`，.md，命名风格与既有方案一致，仅用"哥/弟/妈/爸"家庭称谓、无姓名/证件/联系方式等个人敏感信息。验证方式：文件与全文检查。

## 1.6 非目标（本期明确不做）

- 不出完整逐小时行程（按 §11.10 铁律，待 km 圈定线路后另轮交付）。
- 不做 HTML 页面化、不改 `四季景点/index.html`。
- 不代订/代购门票餐厅，仅提供操作指引。
- 不输出实时路况承诺，车程均为静态估算。

# 二、Design（技术视角 · Conductor 填写）

## 2.1 方案概述

交付物为单一 Markdown 文稿，结构沿用 SPEC-2026-0005 范式：核心结论 → 去过清单与排除说明 → 候选线路对比表 → 分线要点（时间骨架）→ 景点档案（带来源与访问日期）→ 天气研判 → 坑提醒 → 待 km 圈定事项。信息获取官方渠道优先，检索转述类标注"以官方发布为准"。

## 2.2 影响面

| 维度 | 改动 |
|------|------|
| 交付物 | 新增 1 个 .md 文档（`四季景点/待出行方案/`） |
| 服务端/数据模型/对外接口 | 无改动 |
| 敏感与隐私 | 仅使用"哥/弟/妈/爸"家庭称谓，不含姓名/证件/联系方式等个人敏感信息 |

## 2.3 安全与合规自检

- ☑ 不涉及密钥/凭证；☑ 不涉及数据出境（仅公开网页检索）；☑ 不涉及生产数据；☑ 不含未脱敏个人敏感数据。

## 2.4 回滚方案

删除新增文档即可，无其他影响。
