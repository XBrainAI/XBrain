## 多会话并发与共享面写入（并发推进同一规格的写入安全与状态可见性）

v2.12.0 起多个会话可并发推进同一规格（生成侧 + 核验侧并行、跨会话分批）——并发的价值保留，共享面的写入按本节纪律执行，防止重复留痕与过时状态推断（SPEC-2026-0016；背景与方案：SPEC-2026-0015 方案评审稿）。

- **面划分**：**分区面**（各会话独占，零并发冲突）——本会话自己的产出件、委托回执与独立产出件、批次日志/留痕件；**共享面**（多会话可写，按本节协议）——规格 5.1/5.2 留痕、登记区 `_config.md` 与四类工件（SPEC/AUDIT/DELG/TD）编号命名空间、状态快照文件、progress 状态文件、固化件登记面与固化件本体（"多分支并行与汇流"节）。
- **共享面写入协议（四步）**：① **写前重读**——编辑共享面前重读目标小节/文件的最新基线（不凭会话内旧副本；pull 后再读）；② **追加唯一性自检**——追加留痕行前核对同一事件是否已被记录（结构性判据 = 同批次号 + 同事件类型），已存在 → 不得再追加，改在既有行补注或呈报；③ **推送前核对**——提交推送前核对远端基线（pull --rebase 后检查自己的追加是否仍唯一、是否引入重复；无法触达远端（离线/跨 clone）时退化为提交前本地基线核对）；④ **重复处置权受限**——发现自己会话产生的重复行，就地去重并留痕；发现**他人**会话产生的重复 → **不动他人行**，在自己留痕或快照中显式呈报，由收尾对账汇总处置。
- **留痕行结构化标记（批次级事件行的缺省格式）**：共享面追加的批次级事件行，记录列行首采用标记 `〔B<批次号>·<事件类型>·<会话标识>〕`（事件类型开放取值，典型：生成落盘 / QC 委托发出 / QC 回执承接 / 快照更新 / 里程碑）——同批次 + 同事件类型即结构性重复，机器可判定（为二期门禁留口）；未采用标记的行退化为语义判重（按语义判断同一事件是否已记录，拿不准时宁可重复后呈报、不可静默合并）。标记采用率与快照更新及时率列入实施后观测面。
- **规格状态快照（事实源的权威索引，非第二事实源）**：多会话并发推进的规格，维护一份机器可读快照 `*.status.json`——**落位缺省 `.vand-workspace/specs/` 同域，Design 可声明项目自身目录（SPEC-2026-0008 纪律）——两种落位均属共享面、均随项目 git 跟踪、均入 D-32 外部引用扫描（v3.3.0 统一，F-R3-02）；命名 = `<完整编号>.status.json`——完整编号天然唯一，D-32 改名随工件同步双改文件名与 spec_id（F-R3-03）**（与 progress 的"可按需 gitignore"口径不同：快照读者含跨 clone 会话，gitignore 即失去跨 clone 可见性）。schema 字段：spec_id / rev（单调递增）/ stage / current_batches（各并行批次当前动作）/ in_flight（在途委托）/ closed（已闭环委托）/ frozen_artifacts（固化件当前版本索引，每件含**适用域**）/ next_step（记录性字段，供会话读取，非调度授权）/ updated_by / updated_at / base_commit。**事实源不变**——规格 5.2 留痕、委托任务书状态行、固化件登记仍是唯一事实源，快照失真时以事实源为准重建。**更新与对账**：状态变更会话在状态变更落盘的**同一提交**内更新快照；**每次变更必改写 rev / updated_at / updated_by / base_commit 公共字段，且四值聚为单行 `_canary`（如 `"_canary": "rev=N|<时刻>|<人名>:<会话>|<base>"`，v3.3.0 起，F-R2-05；存量多行格式不追溯、不强制迁移）——公共字段即并发冲突金丝雀**：单行聚合保证任意两次并发更新必在该行产生 git 冲突（多行分散时远离行更新会被 git 静默缝合、产出从未存在的缝合态——F-R2-05 实测失效形态），从而强制走重放（基线前进 → 按事实源重放自己的状态变更后提交，JSON 重放远轻于叙事表去重）。**开工对账**（并发规格的会话开工时）：读快照（无快照 → 按"全部委托在途、固化件以目录最新版本为准"的保守假设工作，并提示补建）→ 抽查事实源（在途委托任务书状态行、固化件目录当前版本）→ 差异以事实源为准更正快照并显式列报；**收尾对账**：列报快照与留痕是否已提交、在途委托清单与快照一致性。**与 progress 的关系**：progress 状态文件（`*.progress.json`：批次号/总量/已完成/待办/续作入口说明/历史会话标识）的字段为快照 current_batches / in_flight 的**等价投影**——既有 progress 文件无需迁移，二者可并存（分批续作场景用 progress 记断点，全景状态用快照供对账；见"跨会话委托与续作"节断点续作条）。
- **固化件引用三元**：委托任务书 / 续作引用固化件 = **路径 + 版本 + 适用域**三元（适用域开放取值：切片法域、批次域、语言域等，全域写 none；存量固化件不追溯；归属粒度 = **固化件登记面自声明**）；受托批次必须落在适用域内——不匹配不得引用，换用匹配版本或停下呈报。
- **与既有纪律的关系**：委托关系会话的裁定不变（受托方不写请求方产物与规格留痕——留痕回写是请求方动作，见"跨会话委托与续作"节回注动作链）；本节是其在**平级并行会话**（多生成侧 / 多承接并行）场景下的补齐——共享面所有权不变，写入安全协议与状态可见性补齐。

## 多分支并行与汇流（多人多分支协作的取号对齐、汇流对账与身份约定）

v3.1.0 起（方案：SPEC-003 方案评审稿）。`.vand-workspace/` 随项目 git 跟踪 = **每个分支各持一条演化线**；多人（不同 clone、不同 git 身份）多分支并行派单接单时：取号按四域对齐条款（执行约定 1、"人工审计任务书"节、"跨会话委托与续作"节、"规格写作约定"节——先 pull 再核对、序号 +1 补救），汇流按本节协议。init 产物（project-context.md、todos/`_config.md` 等）由**首个汇流者统一首入库**，其余 clone 同步后以跟踪版为准、不得各自首推同名件（F-R2-04）。

- **汇流动作与义务人（汇流钩子）**：任何使**他人**工作区变更进入当前演化线的 git 动作——merge / rebase / cherry-pick / fast-forward / squash-merge / 向共享分支 push——均为**汇流动作**（不依赖 merge commit 存在）；**义务人 = 动作发起方**（MR 场景=执行合并的人）。汇流动作完成后，义务人在合并结果树上执行下述**汇流对账六步**，逐步留痕于合并提交描述或其后的对账提交——推送已附对账记录的合并提交不另需独立对账提交（v3.1.2）（与开工/收尾钩子并列；收尾列报核对执行情况）。**第 0 步·前置（v3.3.0，F-R2-03/F-R3-05）**：执行六步前先 `git fetch` 并核对本地主干与远端一致——本地基线落后时不得以本地为合并对象（他侧已推内容会被静默漏合）；仅私有分支内同步主干不构成汇流，变更进入共享线（合并/推送共享分支/被他人合并）才触发六步。
- **汇流对账六步**：① **四域唯一性检查**——跑 todos_lint（TD 域）＋三域序号段清单比对（如 `ls .vand-workspace/specs | sed -E 's/^SPEC-([0-9]{3,4})-.*/\1/' | sort | uniq -d`；机器形态 workspace_lint 见 ci/README），发现撞段转四域裁决；② **留痕行与共享面文件判重**——两侧都改过的规格 5.1/5.2 按结构化标记（同批次号+同事件类型）判重，语义重复行就地去重；共享面文件（TD 头部/状态行、`_config.md`、任务书）同入本步授权，按类型处置：配置取并集、任务书双回执两份保留（状态行见③）、TD 承接人唯一性（协调归属留痕）——**授权边界：仅限判重与并集、不得改写行内容（他人行不动，处置留痕）**，留痕记"汇流去重"与操作者（处置细则见 runbook）；③ **任务书状态行与回执合并**——AUDIT/DELG 双回执**两份都保留**（分节存放），状态行以时间指纹晚者/实际终态为准（工件无指纹段内容时以 **git 提交时序**为判据——机器可查证；跨机指纹只作唯一性兜底不作时序权威，F-R2-06）并留痕"双执行合流"；同值静默合流→抽查确认无双执行；④ **状态快照重放**——公共字段冲突后**先修事实源（②③）再重建快照**：rev = max(两侧)+1、base_commit = 汇流后 HEAD、updated_by/at = 重放执行者/时刻，重放留痕于快照所在规格 5.2；⑤ **_config.md 并集**——冲突解值 = 两侧并集（"配置只合并不覆盖"向合并场景的延伸；写法一值一行降低冲突面）；⑥ **列报与盲区预检**——列报两侧新增 open/returned 工件；在线时对"本分支新增工件 × 主干基线"做序号段预检比对，离线如实记录盲区。**modify/delete 形态**（一侧归档/删除、另一侧回写）：归档侧为准，回写内容并入归档件并在合并提交描述留痕，不复活已归档/废弃件；**同名/同 ID 工件分叉**：同源（仅一侧增量）合并留痕，实质分叉（同一治理动作双执行）两份保留＋呈报请求方裁决。逐步操作细则与合并提交描述模板：`template/runbook.md`。
- **四域撞段裁决（D-32 推广，TD 域先例 SPEC-002）**：汇流后任一域出现同序号段双件（文件名异、时间指纹异）→ **指纹较晚者保留原编号、较早者改名**：序号段本地域内递增重取（+1 直至无冲突）、同步改头部编号字段、正文留痕节记"汇流改名：旧编号 → 新编号（分支汇流撞段）"。改名必须过**外部引用扫描**：新旧编号在 specs/、audits/、delegations/、todos/、`*.status.json` 及 `git log --all --grep` 中的引用逐处核对；历史提交/PR 中的旧引用**不改写**，按"已知历史"在改名留痕行登记别名索引。**无主撞号**（较早侧 owner 不在场）：汇流义务人不得代改内容——① 联系 owner 改名后再完成合并，或 ② 经 owner 异步授权（授权留痕于撞段呈报记录）代为执行改名程序；两路不可行 → 挂 TD（触发时机=owner 可用）、MR 标注"含撞段中间态"，收敛前涉事编号不得被新工件引用。**时序语义**：编号"同段内即时间序"**仅限同机**；跨机/跨时区指纹只作唯一性兜底、不作时序权威，撞段裁决维持纯指纹定序。
- **取号锁作用域**：`new-td.py` 排他锁仅**同机同工作树**内互斥；跨 clone / 跨 worktree / 跨分支**不共享锁**——四域取号一律"先 pull 再核对"（各编号条款），撞段按上述裁决收敛。
- **分支删除纪律**：承载未汇流工作区工件的分支不得删除；确需删除前确认该分支 workspace 增量已合并或已归宿（归档/废弃留痕）。业务代码经 squash/cherry-pick 入库而 workspace 提交未入 → MR 自查：提交信息 `spec:` 引用的编号须已存在于目标分支 specs/。
- **固化件与 progress 的分支演化**：固化件本体属共享面，修订须基于主干（或规格所属主开发分支）最新版；同版号分叉——**判定主体 = 汇流义务人、判据 = 语义可合并**（git 行级自动合并成功 ≠ 语义可合并；同段不同行的语义互斥修订不得因无冲突而合并，F-R2-12）：语义可合并则合并后仍称 vN 并在修订记录留痕双侧来源，否则双双升版（vN+1 / vN+2，不用字母后缀）并在修订记录互引；引用三元可选"内容短哈希"第四元（缺省省略）。**progress 分区化**：新增 progress 一律带域后缀命名（`<规格>.progress.<域>.json`，各会话独占文件）；存量 progress 不迁移，按状态快照同款公共字段（rev/updated_at/updated_by/base_commit）兜底。
- **共享分支历史纪律（团队裁剪项）**：共享分支禁 force-push——强烈建议配置为**服务端硬禁**（GitLab Protected Branches / GitHub branch protection 拒绝 force-push；自建裸仓 `receive.denyNonFastForwards=true` 或 pre-receive hook；**注意该配置为全仓粒度**——私有分支 rebase 后的正常强推亦被拒，per-branch 平台保护粒度更准，F-R2-02）——文本纪律防不住历史改写（强推不产生 merge，合并后门禁对其失明），平台拦截是唯一可靠层；未配置平台保护的团队，强推前确认无他人在途为强制义务（v3.1.1）——在途判据：`git for-each-ref refs/remotes/origin --not origin/master` 列未合入主干的远端分支清单，清单非空即有在途（F-R2-11，v3.3.0）；revert 合并提交后视同一次汇流（执行六步）；被 revert 分支再合并前先核对 revert 面与新增变更的叠加语义。
- **多人身份最低约定**：工件人名字段（author/co-authors/reviewers/5.1 参与人/承接人/执行人）统一取 `git config user.name`；字段与所在 git 提交作者的一致性由提交者自证（替他人留痕须以其身份提交或附其独立载体——书面回执/平台留评）；快照 `updated_by` 复合格式 `<人名>:<会话标识>`。

## 规格写作约定（生成或修改规格时）

- 规格写到 **`.vand-workspace/specs/`**（文件名 = `SPEC-<序号段>-<主题>-<YYMMDD-HHMISS.ssss>.md`，编号 = 文件名主体；序号段纪律同执行约定 1——域内唯一自增、首件 000、不回绕、满 999 扩 4 位段，落盘前先 `git pull` 同步远端基线再核对无同号（离线照常落盘、记录盲区并承担汇流对账义务——见"多分支并行与汇流"节）、撞号后写者递增；存量旧格式 `SPEC-<年份>-<四位序号>`、`SPEC-YYYYMMDD-HHMISS.sss` 不追溯，编号永不复用；随项目 git 跟踪，PR 标注 `spec: SPEC-xxx`〔照抄完整编号〕即形成可评审留痕链）；模板与填写指南见 `.vand/template/spec/`（意图写作原则、AC 三类型、影响面条款）；
- **任意任务类型可用**：intent-type 开放取值（调研/评审/方案等可自定义）；非软件任务的影响面写**自有条款**（前缀避开 C，每条声明级别 `→ 升级 **Lx**`）——见 `.vand/template/spec/README.md` 第 5/10 节；
- 需求变更 = 修订规格并重走意图评审，禁止只在代码里"顺手实现"；
- **相似任务不共用规格**：新建规格时在其 1.1 互链引用相似既有规格（作背景证据，范围以本规格为准）；对既有规格的修订/扩展必须重走意图评审——禁止因任务相似而直接挂靠旧规格开工；
- **交付物落位**：规格声明的交付物路径一律为**项目自身目录**（禁止 `.vand-workspace/`）——交付物是项目资产、按项目结构归位，工作区仅承载 VAND 协同工件；
- 作者完成规格草稿后，**主动**为其运行门禁自检并汇报结果：`python .vand/ci/scripts/spec_lint.py <规格文件>`（Windows 亦可 `powershell -File .vand/tools/spec-lint.ps1 <规格文件>`）。
- **送评载体（spec 流程的 audit 阶段）**：L1 及以上规格的意图评审按"人工审计任务书"节产出意图评审任务书送评（起草完成、送评前产出，open）；载体义务不因评审以会话交互进行而豁免（结论可走口头变体——原话摘录留痕 5.1）；L0 豁免不变。

## 范式产物路径（零侵入纪律）

- 意图规格：`.vand-workspace/specs/`（项目资产，随项目 git 跟踪）
- 项目知识：`.vand-workspace/project-context.md`（Design 章版本化引用它）
- 过程待办登记区：`.vand-workspace/todos/`（一 TD 一文件；规格外待办的跨会话登记与时机提醒，见"过程待办登记区与会话例行钩子"节）
- 人工审计任务书：`.vand-workspace/audits/`（需人工复核/裁决/判定/审计时的标准化呈报，见"人工审计任务书"节）
- 会话间委托任务书：`.vand-workspace/delegations/`（把子任务委托给其他 AI 会话的标准化载体，见"跨会话委托与续作"节）
